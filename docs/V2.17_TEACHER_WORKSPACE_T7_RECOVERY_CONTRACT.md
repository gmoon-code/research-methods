# v2.17 Teacher Workspace T7 Recovery Contract

## Purpose

T7 makes Recovery the seventh and final functional area in the authenticated Teacher Workspace.

The first T7 implementation provides a local recovery-inspection and recovery-handoff workflow.

Teacher Workspace may help a teacher determine whether a selected Research Methods Studio project backup is recognized, checksum-valid when the current backup format provides a checksum, and eligible for restoration through the existing student application.

Teacher Workspace does not become a second student-project restoration engine.

The existing student application remains the only interface that replaces the live browser project.

## Existing recovery architecture

Research Methods Studio already provides project recovery through `assets/pilot.js` and `assets/pilot-ui.js`.

The live student project uses the browser-storage key:

`research_methods_studio_v1`

The existing `RMSPilot` API already provides:

- `safeSave`
- `safeLoad`
- `storageReport`
- `backupEnvelope`
- `validateBackup`
- `clearProjectStorage`
- `backupFilename`
- `applyRestore`

T7 must reuse the established backup validation behavior.

T7 must not introduce a competing project-backup format.

T7 must not create a second project-storage key.

T7 must not replace the student application restore sequence.

## Existing backup contract

The current project-backup packet is:

`rms_project_backup`

The current backup version is:

`2.0`

A version 2.0 backup envelope may contain:

- `packet_type`
- `version`
- `mode`
- `created_at`
- `baseline_id`
- `checksum_fingerprint`
- `project`
- `warning`

The existing backup validator also recognizes the legacy full-project form supported by `RMSPilot.validateBackup`.

T7 must preserve that compatibility boundary.

## Full backup boundary

A full version 2.0 project backup may contain:

- raw data
- source notes
- manuscript text
- project configuration
- research decisions
- other student project content

Teacher Workspace must treat the selected full backup as sensitive local data.

T7 must never render full project contents.

T7 must never display raw dataset rows.

T7 must never display manuscript text.

T7 must never display full source notes.

T7 must never display Research Chat history.

T7 must never display participant records.

T7 must never display arbitrary project fields.

T7 must never upload a selected backup.

## Privacy-copy boundary

The existing project backup architecture can create a privacy-minimized copy.

A privacy-minimized copy intentionally omits information required for complete restoration.

The existing validator marks a valid privacy copy as non-restorable.

Teacher Workspace must preserve this result.

A valid privacy copy may be described as:

- recognized
- checksum-valid
- privacy-minimized
- not restorable as a complete project

T7 must never present a privacy copy as a complete recovery backup.

T7 must never provide an override that forces a privacy copy to restore.

## Legacy backup boundary

The existing `RMSPilot.validateBackup` function may recognize a legacy full-project object.

T7 may report a recognized legacy backup as restorable when the existing validator reports it as restorable.

T7 must label the format as legacy.

T7 must not silently convert the selected legacy object into a new persisted project.

Actual restoration remains in the student application.

## Recovery inspection workflow

The first T7 Recovery workflow contains five steps.

1. Select one local JSON backup file.
2. Read the file in browser memory.
3. Parse the selected JSON locally.
4. Validate it through the existing `RMSPilot.validateBackup` behavior.
5. Show a privacy-safe inspection result.

No selected backup file is uploaded.

No selected backup is written into Teacher Workspace storage.

No selected backup is written into the live student project.

No recovery action runs automatically.

## File selection

Recovery accepts one local JSON file at a time.

The file selector must use:

`accept=".json,application/json"`

Selecting a new file replaces the previous in-memory inspection.

The previously inspected backup object must not remain reachable through the public Teacher Workspace state after replacement.

A malformed JSON file must fail safely.

A file that does not satisfy the existing project-backup validation behavior must fail safely.

Failure must not modify student project storage.

Failure must not clear Teacher Workspace state.

Failure must not end the signed teacher session.

## File-size boundary

T7 must apply a bounded client-side file-size check before reading a selected backup.

The first implementation uses a maximum selected file size of 25 MiB.

The exact byte ceiling is:

`26214400`

A file larger than this boundary must be rejected before `File.text()` is called.

This limit concerns Teacher Workspace inspection only.

It does not change the student application's existing project-storage or backup behavior.

## Existing validator dependency

Teacher Workspace may load `assets/pilot.js` to access the existing `RMSPilot.validateBackup` function.

T7 must not call these `RMSPilot` functions from Teacher Workspace:

- `safeSave`
- `safeLoad`
- `clearProjectStorage`
- `applyRestore`
- `backupEnvelope`

T7 must not call `storageReport` against the live student project key.

T7 must not call `localStorage` directly.

T7 must not call `sessionStorage` directly for Recovery behavior.

Teacher authentication continues to use the existing `RMSTeacherSession` implementation.

## No student-storage access

Teacher Workspace Recovery must never read:

`research_methods_studio_v1`

Teacher Workspace Recovery must never write:

`research_methods_studio_v1`

Teacher Workspace Recovery must never read or write:

`research_methods_studio_v1_recovery_v2`

Teacher Workspace Recovery must never read or write:

`research_methods_studio_v1_pilot_meta_v2`

Teacher Workspace Recovery must never clear student onboarding state.

Teacher Workspace Recovery must never enumerate browser storage searching for student projects.

## No destructive operations

T7 contains no delete-project action.

T7 contains no clear-project action.

T7 contains no reset-project action.

T7 contains no overwrite-project action.

T7 contains no direct restore button that mutates student project storage.

T7 contains no automatic rollback.

T7 contains no browser-storage cleanup command.

Selecting or inspecting a backup must be reversible by clearing the selected file from the page.

## Existing student restore sequence

The current student recovery interface performs the authoritative restoration sequence.

The student recovery interface:

1. reads the selected file
2. parses JSON
3. calls `RMSPilot.validateBackup`
4. requires a valid result
5. requires `restorable` to be true
6. asks for explicit confirmation
7. calls `RMSPilot.applyRestore`
8. replaces the in-memory project object
9. saves through the existing project save function
10. reports save failure if the restored project cannot be written
11. reloads the student application after a successful save

T7 must not duplicate this mutation sequence.

T7 must direct a teacher or student to the existing student-site recovery flow for actual restoration.

## Recovery handoff

When the selected backup is valid and restorable, Teacher Workspace may display an action labeled:

`Open student recovery`

The action may open the existing student site.

The action must not transfer the selected backup automatically.

The user must select the backup again in the student recovery interface.

The handoff must explain that the student application performs the actual restore and asks for confirmation before replacing the current browser project.

T7 must not imply that the project has already been restored.

## Student-site navigation

Recovery may use the existing student-site destination:

`./`

The handoff may open the student site in a new browser tab or use the existing View student site behavior.

Opening the student site must not clear the signed teacher session.

Opening the student site must not write recovery data to storage.

## Safe inspection model

Teacher-facing backup inspection must be reduced to an allowlisted model before rendering.

The proposed pure public function is:

`deriveTeacherRecoveryInspection(input)`

The function belongs in:

`assets/teacher-workspace-data.js`

It must remain deterministic and browser-independent.

The input may contain only these explicit values:

- file name
- file size in bytes
- parse success boolean
- validator available boolean
- validation success boolean
- restorable boolean
- backup mode
- legacy boolean
- packet type
- packet version
- created-at text
- baseline identifier
- checksum fingerprint text
- validator error text

The function must not receive:

- the project object
- raw JSON text
- raw data
- source notes
- manuscript sections
- participant records
- student Research Chat content
- arbitrary backup properties

## Safe inspection output

The public T7 inspection model should contain:

- `file`
- `format`
- `integrity`
- `recovery`
- `privacy`
- `message`

### File

`file` may contain:

- `name`
- `size_bytes`
- `within_size_limit`

The file name is displayed only as local file-selection context.

T7 must not parse identity meaning from the file name.

### Format

`format` may contain:

- `recognized`
- `packet_type`
- `version`
- `mode`
- `legacy`

Unsupported or missing format data remains explicit.

### Integrity

`integrity` may contain:

- `parse_ok`
- `validator_available`
- `validation_ok`
- `checksum_verified`

For version 2.0 backup envelopes, a successful existing validator result means the checksum fingerprint matched.

For recognized legacy backups, checksum status must be represented as unavailable.

T7 must not invent a checksum result for legacy backups.

### Recovery

`recovery` may contain:

- `restorable`
- `restore_location`

`restore_location` is always:

`student_site`

Teacher Workspace itself is never the restore location.

### Privacy

`privacy` must expose fixed booleans confirming:

- project_contents_exposed is false
- raw_data_exposed is false
- manuscript_exposed is false
- source_notes_exposed is false
- chat_transcripts_exposed is false
- live_student_storage_accessed is false
- backup_uploaded is false

### Message

The model may provide one concise safe status message.

The message must be generated from allowlisted state.

The message must not include arbitrary validator input or arbitrary project content.

A validator error may be mapped to a small fixed set of safe teacher-facing messages.

## Error-message boundary

Raw exception text from JSON parsing must not be shown directly.

Raw browser file-system details must not be shown directly.

Arbitrary values from the backup project must not appear in errors.

T7 may use fixed messages such as:

- The selected file is not valid JSON.
- The selected file is not a recognized Research Methods Studio project backup.
- The backup checksum could not be verified.
- This privacy-minimized copy is valid but cannot restore a complete project.
- This backup is valid and can be restored through the student site.
- This legacy backup is recognized and can be restored through the student site.
- Recovery inspection is unavailable because the existing backup validator did not load.
- The selected file is too large for Teacher Workspace inspection.

## Checksum reporting

T7 must distinguish checksum validation from generic recognition.

For `rms_project_backup` version `2.0`:

- validator success means checksum verified
- validator failure means checksum is not verified

For recognized legacy backups:

- checksum status is unavailable
- T7 must not display Verified checksum

T7 must not implement a competing checksum algorithm in Teacher Workspace UI code.

The existing `RMSPilot.validateBackup` behavior remains authoritative.

## Backup metadata exposure

T7 may display these version 2.0 envelope values when present and safely typed:

- packet type
- version
- mode
- created time
- baseline identifier
- checksum fingerprint

T7 must display them with `textContent`.

T7 must not use `innerHTML` for selected-file metadata.

T7 must not render the `project` field.

T7 must not traverse the `project` field for teacher display.

## Created-at handling

A safely typed `created_at` value may be displayed as inert text.

T7 does not need to reinterpret or correct the timestamp.

Missing `created_at` remains unavailable.

T7 must not reject an otherwise valid existing backup solely because `created_at` is missing.

## Baseline identifier handling

A safely typed `baseline_id` may be displayed as inert text.

The baseline identifier is informational.

T7 must not use the baseline identifier to approve, reject, rank, or grade student work.

T7 must not change measurement-baseline rules.

## Teacher Workspace transient-state recovery

Teacher Workspace itself remains intentionally local and transient.

T7 must clearly explain:

- imported `rms_student_review` packets exist only in memory
- teacher review drafts exist only in memory until downloaded
- assignment setup drafts exist only in memory until downloaded
- page reload cannot recreate unsaved in-memory teacher work
- previously downloaded files can be re-imported through their existing workflows

T7 must not claim that Teacher Workspace has server backups.

T7 must not claim that imported review packets are automatically recoverable after reload.

T7 must not create a hidden Teacher Workspace autosave system.
