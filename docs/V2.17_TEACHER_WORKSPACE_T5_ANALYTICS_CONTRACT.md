# v2.17 Teacher Workspace T5 Analytics Contract

## Status

T5 defines the first functional Analytics area in the authenticated Teacher Workspace.

T5 is an aggregate workflow-status view over locally imported `rms_student_review` version `1.7` packets.

It does not create a grading system, competency dashboard, student ranking system, predictive model, statistical analysis system, or permanent class database.

The T5 Analytics area must remain subordinate to teacher judgment.

## Recovery point

T5 begins from the frozen T4 recovery point:

- commit `86cd59a7b8e32ef81cde63fa84b02b32e3a4e8df`
- tree `5ec2ca15485f94662e2225829243efc1becda4dc`

T4 remains frozen while T5 is developed.

## Primary purpose

T5 helps a teacher answer descriptive class-management questions from the review packets currently imported into the Teacher Workspace.

Examples include:

- how many imported projects explicitly report each stage as ready
- how imported projects are distributed across milestone states
- how many imported projects currently report review, revision, blocker, ethics, protocol, or stored-analysis conditions
- how many imported projects are represented in each reported course section
- how many imported projects report included or verified literature sources

These are packet-derived workflow summaries.

They are not measures of student ability, achievement, learning, quality, effort, likelihood of success, or final performance.

## Source of truth

T5 may derive analytics only from the normalized `rms_student_review` version `1.7` packets already accepted by `assets/teacher-workspace-data.js`.

The imported packet collection remains the sole T5 data source.

T5 must not read student projects directly.

T5 must not read raw datasets.

T5 must not read full manuscripts.

T5 must not read full source notes.

T5 must not read Research Chat transcripts.

T5 must not fetch additional student data.

T5 must not infer missing packet content from other browser state.

## Explicit separation from the existing analytics engine

`assets/analytics.js` is a student-project statistical analysis engine.

T5 Teacher Analytics must not call, import, duplicate, or depend on `window.RMSAnalytics`.

T5 must not run descriptive statistics, hypothesis tests, correlations, regressions, assumption checks, effect estimates, or statistical recommendations over student projects.

The presence of `assets/analytics.js` does not authorize class-level statistical comparison of students.

## Explicit separation from the competency system

The existing v1.8 competency and learning-evidence model is outside T5.

T5 must not consume `competency_snapshot`.

T5 must not consume automated Independent Reasoning, Supported Performance, Scaffold Load, or revision-cycle indicators.

T5 must not consume teacher competency ratings.

T5 must not calculate competency averages.

T5 must not combine automated indicators with teacher judgments.

T5 must not describe any aggregate as competency, mastery, proficiency, ability, achievement, or learning gain.

The provisional v1.8 competency framework remains separate from T5.

## Fields that T5 may use

T5 may use only the following normalized packet information:

- `project_id`
- `student_alias` only where an existing non-analytics navigation action requires it
- `course_section`
- `stage_ready`
- milestone `id`
- milestone `title`
- milestone `state`
- milestone blockers
- milestone checkpoint status
- source `included`
- source `verified`
- method `ethicsStatus`
- method `locked`
- analysis `stored_runs`

The Analytics display should aggregate these fields.

Student names or aliases must not become chart categories, ranking rows, or comparison axes.

## Fields that T5 must not interpret as performance

The following normalized fields must not be used as student-performance analytics in T5:

- `methods.score`
- `methods.label`
- `methods.critical`
- `methods.warning`
- `analysis.imported_rows`
- `analysis.primary_estimand`
- `analysis.primary_result`
- writing section word counts
- teacher feedback comment text
- checkpoint comment text
- checkpoint conditions text
- source theme text
- project research-question text
- project topic text
- full writing content
- competency data

Their presence in a review packet does not authorize class-level scoring or comparison.

## T5 aggregate model

T5 should expose one pure derivation entry point:

`deriveTeacherAnalytics(packets)`

The returned object must be deterministic, immutable, and browser-independent.

It must contain only aggregate packet-derived status information.

The first T5 analytics model should contain the following sections.

### Imported-project denominator

`project_count`

This is the number of valid normalized review packets currently imported.

No percentage may be displayed without the corresponding imported-project denominator being visible or directly available.

### Stage readiness

`stage_readiness`

This contains exactly stages 1 through 18.

Each row contains:

- `stage`
- `ready_projects`
- `project_count`

`ready_projects` counts only packets that explicitly report that stage as `true`.

Missing, malformed, absent, or non-true stage information must not be interpreted as failure, lack of competence, non-completion, or student difficulty.

The UI must explain that stage readiness is workflow status reported by the packet.

### Milestone-state distribution

`milestone_states`

This contains exactly M1 through M5.

Each milestone contains counts for the canonical workflow states:

- `blocked`
- `student_ready`
- `awaiting_teacher`
- `revision_requested`
- `approved`
- `complete`
- `other_or_missing`

Every valid imported packet contributes exactly once to each milestone distribution.

A missing milestone record, unknown state, or noncanonical state contributes to `other_or_missing`.

The system must not silently convert missing or unknown states into `blocked`, `incomplete`, or any other negative interpretation.

### Workflow condition counts

`workflow_counts`

The first T5 implementation may report:

- projects with at least one `awaiting_teacher` milestone
- projects with at least one `revision_requested` milestone
- projects with at least one milestone blocker
- projects explicitly reporting `methods.ethicsStatus === "teacher_review"`
- projects explicitly reporting `methods.ethicsStatus === "do_not_facilitate"`
- projects explicitly reporting `methods.locked === true`
- projects reporting `analysis.stored_runs > 0`

Each measure counts projects, not events, unless its label explicitly states otherwise.

Missing optional fields remain unknown.

They must not be treated as affirmative or negative evidence.

### Course-section counts

`course_sections`

This may group imported projects by their packet-reported `course_section`.

Rows contain:

- `course_section`
- `project_count`

Blank or missing course section values use one neutral label such as `Unspecified`.

Rows must use deterministic lexical ordering.

Course-section counts are organizational summaries.

They must not be used to compare instructional quality or student performance between sections.

### Literature-status counts

`literature_status`

The first T5 implementation may report:

- projects reporting `sources.included > 0`
- projects reporting `sources.verified > 0`

These are presence counts only.

T5 must not average source counts across students.

T5 must not rank projects by number of sources.

T5 must not treat a larger source count as better research quality.

## No student ranking

T5 must not provide:

- leaderboards
- rank order
- top or bottom students
- strongest or weakest students
- best or worst projects
- percentile ranks
- quartiles of student performance
- comparative performance labels
- traffic-light student ratings
- star ratings
- score bands
- student performance tiers

Sorting students by a purported performance measure is prohibited.

Existing deterministic ordering used for navigation remains allowed when it is clearly non-performance-based.

## No risk or prediction model

T5 must not generate:

- at-risk labels
- risk scores
- success probabilities
- completion probabilities
- failure probabilities
- intervention predictions
- likely outcome labels
- dropout predictions
- automated priority scores

A project with blockers or revision requests may be counted descriptively.

The system must not convert those statuses into a prediction about the student.

## No grading

T5 must not create or infer:

- grades
- points
- percentages as grades
- letter grades
- rubric scores
- weighted scores
- competency grades
- completion grades
- participation grades
- penalties
- bonuses

T5 may display counts and descriptive workflow distributions only.

## No performance composite

T5 must not combine stage readiness, milestone state, source counts, methods indicators, analysis records, or writing metadata into a composite number.

There is no T5 overall score.

There is no T5 research-quality score.

There is no T5 progress score.

There is no T5 student-health score.

There is no T5 class-performance score.

## No inferential comparison

T5 must not calculate statistical significance, correlations, regression models, effect sizes, confidence intervals, hypothesis tests, or inferential comparisons among students or course sections.

T5 is descriptive workflow reporting only.

## Assignment Setup boundary

T4 assignment profiles remain independent local files.

T5 does not join assignment due dates to student review packets.

T5 therefore does not calculate:

- overdue students
- late projects
- days late
- on-time rates
- deadline compliance
- pacing scores

A later milestone would need an explicit, validated association model before such analysis could be considered.

## Review Queue boundary

T5 may reproduce aggregate counts that are already derived from packet workflow states.

T5 must not change Review Queue ordering.

T5 must not write queue flags.

T5 must not change checkpoint state.

T5 must not approve or request revision.

T5 must not create teacher feedback.

## Student Inspector boundary

T5 must not mutate the selected project.

T5 must not change Student Inspector state.

A future explicit navigation control may open an existing project in the Inspector, but aggregate charts themselves must remain read-only.

## Data lifecycle

T5 analytics exist only while review packets are present in the current Teacher Workspace page.

T5 must use the existing `importedPackets` page-memory collection.

T5 must not add:

- `localStorage`
- new `sessionStorage` records
- IndexedDB
- cookies
- Cache Storage
- server storage
- database storage
- file-system persistence
- cloud synchronization

The established teacher authentication session keys remain unchanged and outside T5 analytics state.

## Network boundary

T5 must not add any network request.

T5 requires no new Worker route.

T5 requires no Worker deployment.

T5 requires no API key.

T5 requires no paid service.

T5 requires no database.

T5 requires no new backend infrastructure.

## Privacy

T5 must operate only on the privacy-limited review packet.

It must not expose or reconstruct:

- raw dataset rows
- full manuscripts
- full source notes
- Research Chat transcripts
- authentication credentials
- teacher session tokens
- hidden student data not present in the review packet

T5 must not create a new analytics export during the first implementation.

The first T5 milestone is view-only.

## Missing data

Missing information must remain missing or unknown.

T5 must not silently replace missing optional information with a negative student judgment.

Examples include:

- missing stage readiness does not mean failed
- missing locked-protocol status does not mean unlocked
- missing ethics status does not mean cleared
- missing analysis information does not mean analysis failure
- missing source counts do not mean no research was performed

UI copy must distinguish explicit packet reports from unavailable information where the distinction matters.

## Determinism

For the same normalized packet collection, `deriveTeacherAnalytics` must return the same substantive aggregate result.

Results must not depend on:

- current time
- random values
- browser locale
- DOM state
- current selected student
- assignment draft state
- teacher review draft state
- network responses

Deterministic ordering must be used for stages, milestones, and course sections.

## Immutability

`deriveTeacherAnalytics` must not mutate:

- imported packet arrays
- normalized packet objects
- review drafts
- assignment drafts
- student projects

The returned analytics object and nested analytics structures must be frozen.

## T5 UI

The existing Analytics navigation area becomes functional.

The UI should remain readable before any packets are imported.

At zero imported projects it should explain that analytics are generated from locally imported review packets.

The first functional Analytics view should provide:

- imported-project denominator
- workflow condition summary
- stage-readiness view for stages 1 through 18
- milestone-state distributions for M1 through M5
- course-section project counts
- literature-status presence counts
- interpretation notes

The UI must use text-safe DOM construction.

Untrusted packet text must use `textContent` or equivalent safe node creation.

No dynamic `innerHTML` or `insertAdjacentHTML` may be introduced.

## Visual interpretation

Charts, bars, counts, or tables may be used when they improve readability.

Any visual encoding must represent descriptive counts only.

Color must not imply:

- good versus bad students
- passing versus failing
- strong versus weak
- safe versus unsafe student ability
- predicted success or failure

Workflow statuses may be distinguished visually when labels remain explicit.

The view must remain understandable without relying on color alone.

## Accessibility

T5 must preserve:

- keyboard navigation
- visible focus behavior
- semantic headings
- meaningful text labels
- screen-reader-readable counts
- responsive layout

Charts must have equivalent textual information.
