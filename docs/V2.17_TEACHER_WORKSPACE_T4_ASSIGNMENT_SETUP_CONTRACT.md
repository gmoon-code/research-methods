# Research Methods Studio v2.17 Teacher Workspace

## T4 Assignment Setup Contract

T3 is frozen at commit `f50b031b79abf69b126f332257e72c2e9b6fbff3`.

## Purpose

T4 makes the existing Assignment Setup area functional.

A teacher may create an assignment profile around the existing Research Methods Studio journey, inspect it, export it locally as JSON, and import it again into the Teacher Workspace.

T4 does not change the core student research route.

## Existing journey boundary

The existing student journey remains authoritative.

It contains

- 18 stages
- M1 Question Ready
- M2 Evidence Base Ready
- M3 Method Approved
- M4 Analysis Ready
- M5 Paper Ready for Final Review

T4 must not allow a teacher to

- add or remove stages
- renumber stages
- add or remove milestones
- change milestone stage membership
- change which milestones require teacher review
- rewrite milestone completion logic
- alter existing student progress
- alter checkpoint status
- create automatic approvals or revisions

Assignment Setup provides context and scheduling around the fixed journey.

## Assignment setup packet

T4 introduces one teacher-side local configuration format

- packet type `rms_assignment_setup`
- version `1.0`

The first T4 packet contains only

- `packet_type`
- `version`
- `created_at`
- `assignment_id`
- `title`
- `course_section`
- `teacher_display_name`
- `student_instructions`
- `teacher_notes`
- `milestone_due_dates`

The packet must use an explicit allowlist.

## Fixed packet values

`packet_type` must equal `rms_assignment_setup`.

`version` must equal `1.0`.

`created_at` is generated at export time as an ISO-8601 timestamp.

## Assignment identity

`assignment_id` is required.

It identifies one assignment configuration and is separate from student `project_id`.

It must not contain credentials, teacher-session tokens, or student identifiers.

Importing another packet with the same `assignment_id` may replace the current in-memory assignment profile only through an explicit teacher action.

## Assignment title

`title` is required teacher-authored text.

It names the assignment shown in Assignment Setup.

T4 must not infer a title from a student project.

## Course or section

`course_section` is optional teacher-authored text.

It may correspond to the existing student `journey.courseSection` field.

T4 does not automatically rewrite imported student packets or student projects with this value.

## Teacher display name

`teacher_display_name` is optional teacher-authored text.

It is not an authentication credential.

It must never contain or expose the teacher access code or signed teacher-session token.

## Student instructions

`student_instructions` is optional teacher-authored text.

It may contain assignment-specific directions for students.

T4 does not inject these instructions into student projects.

Direct delivery to students belongs to a later explicitly defined integration milestone.

## Teacher notes

`teacher_notes` is optional teacher-only text.

It is included only in the teacher assignment setup packet.

Teacher notes must not be copied automatically into student review packets or teacher feedback packets.

## Milestone due dates

`milestone_due_dates` is an object keyed only by

- `M1`
- `M2`
- `M3`
- `M4`
- `M5`

Each value is either

- an empty string
- a valid calendar date in `YYYY-MM-DD` format

T4 does not create due dates for individual stages.

T4 due dates are planning information only.

A missed due date must never automatically

- block a student
- change milestone state
- request revision
- approve work
- assign a grade
- alter queue priority

## No grading configuration

The first T4 implementation does not include

- point values
- percentages
- grading weights
- letter grades
- competency ratings
- rubric scores
- automated grading
- late penalties

Those capabilities require a separate contract if added later.

## In-memory state

The active Assignment Setup draft exists only in JavaScript memory for the current Teacher Workspace page session.

T4 must not persist assignment configuration in

- localStorage
- sessionStorage
- IndexedDB
- cookies
- Cache Storage
- the Cloudflare Worker
- another server
- a database

The existing signed teacher session may continue to use its established sessionStorage keys.

Assignment configuration must not be stored in those authentication keys.

## Local import

The teacher may import an `rms_assignment_setup` version `1.0` JSON file.

Import must validate the complete packet before replacing the current draft.

Malformed or unsupported packets must fail closed.

Import must not change student projects.

Import must not change teacher review drafts.

Import must not upload the file.

## Local export

The teacher may preview the validated assignment packet before download.

Export requires an explicit teacher action.

Suggested filename

`rms-assignment-setup-<assignment_id>.json`

Unsafe filename characters must be sanitized.

Export must not send assignment content over the network.

## Validation

Validation must reject

- non-object packets
- wrong packet type
- wrong version
- missing or empty `assignment_id`
- missing or empty `title`
- unexpected milestone IDs
- malformed milestone due-date values
- malformed top-level fields

Validation must not silently repair unsupported values.

## Text safety

All imported and teacher-authored assignment strings are untrusted text.

The UI must render them through text-safe DOM operations.

T4 must not introduce dynamic `innerHTML` or `insertAdjacentHTML` for assignment content.

Downloaded JSON must be created from validated data structures.

## Authentication

Assignment Setup remains behind the existing signed teacher-session verification.

Assignment controls must not initialize before successful teacher verification.

No query parameter or client-only role flag may activate Assignment Setup.

## Network boundary

T4 adds no assignment network request.

Allowed Teacher Workspace network behavior remains the existing signed teacher-session verification.

T4 adds no Worker route, Worker secret, database, or paid infrastructure.

## Relationship to student projects

T4 does not directly modify student project data.

T4 does not change

- `studentAlias`
- `courseSection`
- research question
- design
- stage readiness
- checkpoints
- methods
- analysis
- writing
- teacher feedback

A future student-assignment integration requires a separate contract.

## Relationship to T2 and T3

T4 must not change

- student review packet version `1.7`
- teacher feedback packet version `1.7`
- T2 Overview
- T2 Review Queue
- T2 Student Project Inspector
- T3 teacher review decisions
- T3 feedback export
- project-switch protections

## Teacher Workspace navigation

The seven primary areas remain

- Overview
- Review Queue
- Students
- Assignment Setup
- Analytics
- Chat Controls
- Recovery

T4 makes the existing Assignment Setup area functional.

No eighth primary area is added.

Analytics, Chat Controls, and Recovery remain later milestones.

## Pure data layer

Assignment validation and packet construction should live in pure data functions.

The data layer must not perform

- DOM operations
- authentication
- browser storage
- downloads
- network requests

Required capabilities include

- create an empty assignment draft
- validate an assignment draft
- update assignment fields without mutation
- update milestone due dates without mutation
- validate an imported assignment packet
- build a validated `rms_assignment_setup` version `1.0` packet

## Required data tests

Tests must cover

- exact packet type and version
- required assignment identity
- required title
- optional text fields
- all five permitted milestone IDs
- rejection of unknown milestone IDs
- valid and invalid date formats
- immutable updates
- exact export allowlist
- invalid import rejection
- no student-project fields in assignment export
- frozen output structures

## Required static UI tests

Tests must verify

- authentication remains required
- Assignment Setup uses the pure data API
- assignment state remains page-memory-only
- no new persistence
- no assignment network request
- no unsafe dynamic HTML
- explicit preview and download
- local JSON import
- seven primary areas remain unchanged
- Analytics, Chat Controls, and Recovery remain reserved

## Required real-browser QA

Real-browser QA must verify

- authenticated teacher can open Assignment Setup
- teacher can create a valid assignment
- all five milestone due dates can be entered
- invalid dates are rejected
- preview matches the validated packet
- local download matches preview
- exported filename is sanitized
- exported packet can be imported back into Assignment Setup
- untrusted assignment text remains inert
- assignment data does not enter persistent browser storage
- assignment data crosses no new network boundary
- student project and teacher review state remain unchanged

## Completion criteria

T4 is complete only when

- the contract is implemented
- `rms_assignment_setup` version `1.0` is validated and exported locally
- the fixed 18-stage and five-milestone journey remains unchanged
- no grading or competency-rating configuration is added
- no student project is modified
- assignment drafts remain page-memory-only
- no Worker route, database, or assignment network path is added
- all focused and regression tests pass
- real-browser Assignment Setup QA passes
- a clean local recovery commit is created
- nothing is pushed or merged without explicit authorization
