# Research Methods Studio v2.17 Teacher Workspace T2 Data Contract

## Status

Development contract for the first functional Teacher Workspace milestone after
the authenticated T1 shell.

T2 is limited to local processing of existing v1.7 student review packets.

The packet format remains unchanged.

## T2 purpose

T2 will make three Teacher Workspace areas useful.

1. Overview
2. Review Queue
3. Student Project Inspector

These areas will consume only information already exported in the existing
rms_student_review version 1.7 packet.

T2 will not add a database, server-side student storage, student accounts,
expanded student packets, Worker routes, or Research Chat transcript access.

## Source-of-truth packet

The only accepted student packet type during T2 is

- packet_type equal to rms_student_review
- version equal to 1.7

The existing student export remains the source of the packet.

T2 must not change exportStudentPacket or packet version 1.7.

T2 must not require students to export additional information.

## Existing v1.7 packet surface

The current packet may contain the following top-level information.

### Project identity and context

- exported_at
- project_id
- student_alias
- course_section
- project_name
- context
- research_question
- question_type
- design
- topic

### Stage and milestone information

- stage_ready
- milestones

Each milestone may contain

- id
- title
- state
- blockers
- warnings
- checkpoint

Checkpoint information may contain

- status
- requestedAt
- reviewedAt
- teacher
- comment
- conditions

### Source summary

The sources object may contain

- total
- included
- verified
- themes

T2 must not imply that full source records, source notes, PDFs, quotations, or
full source text were inspected.

### Methods summary

The methods object is the existing Methods Lab summary produced for the packet.

It may include

- available
- score
- label
- critical
- warning
- ethicsStatus
- locked

T2 must preserve the difference between local software diagnostics and teacher
judgment.

### Analysis summary

The analysis object may contain

- dataset_file
- imported_rows
- stored_runs
- primary_estimand
- primary_result

These are metadata and selected summary fields.

T2 must not display, reconstruct, request, or imply access to raw dataset rows.

### Writing summary

The writing object may contain

- paper_audit
- section_words

T2 must not display or imply access to full manuscript text from this packet.

### Existing teacher feedback

The packet may contain teacher_feedback previously imported into the student
project.

T2 may display this history as read-only context.

T2 must not silently alter it.

### Competency snapshot

The packet may contain competency_snapshot.

The first T2 Student Project Inspector will not use this field for grading,
ranking, queue priority, or automatic teacher decisions.

Detailed competency presentation is deferred to the separate Analytics
milestone so software-generated evidence can remain visibly separate from
teacher judgment.

## Privacy boundary

The packet privacy boundary remains unchanged.

The current packet intentionally omits

- raw dataset contents
- full paper text
- full source text
- full source notes
- Research Chat transcripts

The Teacher Workspace must state that its view is based on an imported review
packet and that omitted work has not been inspected.

No T2 screen may imply otherwise.

## T2 persistence boundary

Imported packets exist only in memory for the current Teacher Workspace page
session.

T2 must not store imported packet contents in

- localStorage
- sessionStorage
- IndexedDB
- cookies
- a remote server
- the Cloudflare Worker

Reloading or leaving the Teacher Workspace may clear the imported packet set.

Persistent class storage requires a separately reviewed later design.

## Packet validation boundary

The old Teacher Dashboard performs only a minimal packet_type and version
check.

The dedicated Teacher Workspace will add a read-only validation and
normalization layer before a packet can enter Overview, Review Queue, or the
Student Project Inspector.

Validation must not mutate the imported source object.

### Hard rejection

A file must be rejected when any of these conditions apply.

- Parsed content is not an object.
- packet_type is not rms_student_review.
- version is not 1.7.
- project_id is absent, empty, or not a string.
- milestones is absent or is not an array.
- A milestone entry is not an object.
- A milestone has no usable id.
- A milestone state is present with a type other than string.
- blockers is present with a type other than array.
- warnings is present with a type other than array.
- checkpoint is present with a type other than object.
- methods is present with a type other than object.
- analysis is present with a type other than object.
- writing is present with a type other than object.
- sources is present with a type other than object.

A rejected packet must not contribute to class counts or queue results.

The interface must explain that the file could not be imported.

### Safe normalization

Optional missing values may be normalized only for display and derived counts.

Examples include

- missing student_alias becomes an empty display value
- missing course_section becomes an empty display value
- missing blockers becomes an empty array
- missing warnings becomes an empty array
- missing checkpoint becomes an empty display-safe checkpoint object
- missing source summary values display as unavailable
- missing analysis summary values display as unavailable

Normalization must never create evidence that was absent from the packet.

The original imported object remains unchanged.

## Duplicate project handling

project_id is the T2 deduplication key.

When a newly imported valid packet has the same project_id as an already
imported packet, the newer import replaces the earlier in-memory copy.

The interface must report that the project was updated.

T2 must not merge fields from two versions of the same project.

The most recently imported whole packet becomes the current review snapshot.

## Overview contract

Overview reports project-level or checkpoint-level counts derived only from
valid imported packets.

### Imported projects

Count unique valid project_id values currently held in memory.

### Checkpoints awaiting review

Count milestone records whose state is awaiting_teacher.

This is a checkpoint count and may be greater than the number of projects.

### Revision requests

Count milestone records whose state is revision_requested.

This is also a checkpoint count.

### Projects with unresolved blockers

Count unique projects where at least one milestone contains one or more
blockers.

Do not count blocker strings as separate projects.

### Ethics teacher-review cases

Count unique projects where methods.ethicsStatus equals teacher_review.

### Do-not-facilitate cases

Count unique projects where methods.ethicsStatus equals do_not_facilitate.

### Locked protocols

Count unique projects where methods.locked is true.

### Projects with stored analysis records

Count unique projects where analysis.stored_runs is a finite number greater
than zero.

### Overview interpretation

Overview is instructional triage.

It must not

- rank students
- calculate grades
- calculate class standings
- identify a strongest or weakest student
- convert software diagnostics into teacher ratings
- treat a missing field as evidence of failure

## Review Queue contract

Review Queue is generated from valid imported packets.

Queue membership is derived from explicit packet evidence.

A project may appear under more than one queue filter when more than one
condition applies.

The interface must explain every queue flag.

### Awaiting review

Include a project when at least one milestone state equals awaiting_teacher.

The reason must identify the affected milestone or milestones.

### Revision requested

Include a project when at least one milestone state equals
revision_requested.

The reason must identify the affected milestone or milestones.

### Ethics review

Include a project when methods.ethicsStatus equals teacher_review.

The reason must state that the packet reports teacher or institutional review
as required.

### Do not facilitate

Include a project when methods.ethicsStatus equals do_not_facilitate.

The interface must make this condition visually prominent.

The Teacher Workspace must not convert this software-generated status into a
teacher approval or final institutional decision.

### Blocked

Include a project when at least one milestone contains one or more blockers.

The queue reason may show the first blocker and the number of additional
blockers.

The full blocker list remains available in the Student Project Inspector.

### No immediate teacher action

Include a project in this filter only when none of the following apply.

- awaiting review
- revision requested
- ethics review
- do not facilitate
- blocked

This label means that the imported packet contains no current T2 queue flag.

It does not mean that the project is complete, correct, approved, or safe.

## Review Queue ordering

T2 must not create a student performance ranking.

Within a queue filter, the default deterministic order will use

1. course_section
2. student_alias when present
3. project_name when present
4. project_id

Safety status may be surfaced visually without using it to rank academic
performance.

A later teacher-selected sort may be added separately.

## Student Project Inspector contract

The Student Project Inspector is a read-only view of one valid imported packet.

It must display a persistent notice that the view is based on an exported
review packet and does not contain all student work.

### Inspector header

The header may display

- student_alias
- project_id
- course_section
- project_name
- exported_at

The project_id must remain visible even when an alias exists so packet identity
is unambiguous.

### Research overview

The inspector may display

- context
- topic
- research_question
- question_type
- design

### Stage progress

The inspector may display stage_ready as a read-only 1 through 18 progress
summary.

A missing stage value means unavailable or not marked ready.

It must not be interpreted as a grade.

### Milestones

For each milestone the inspector may display

- id
- title
- state
- blockers
- warnings
- checkpoint status
- checkpoint requestedAt
- checkpoint reviewedAt
- checkpoint teacher
- checkpoint comment
- checkpoint conditions

T2 does not edit these values in place.

Teacher decisions continue to use an explicit feedback-packet workflow in a
later functional step.

### Sources

The inspector may display

- total source count
- included source count
- verified source count
- themes

It must state that individual source records and source notes are not contained
in the review packet.

### Methods

The inspector may display the existing methods summary fields.

Software-generated method score, label, critical count, warning count, and
ethics status must be labeled as packet diagnostics.

They must remain visually distinct from future teacher decisions.

### Analysis

The inspector may display

- dataset_file
- imported_rows
- stored_runs
- primary_estimand
- primary_result

The inspector must state that raw dataset rows are not included.

### Writing

The inspector may display

- paper_audit
- section_words

The inspector must state that full paper text is not included.

### Teacher feedback history

Existing teacher_feedback may be shown read-only.

The inspector must not silently modify or append feedback.

### Competency evidence

The first T2 Inspector will not render competency_snapshot.

Its eventual presentation belongs in Analytics and requires explicit visual
separation between software-generated indicators and teacher ratings.

## Empty and missing states

Missing optional packet fields must produce neutral language such as

- Not provided in this review packet
- No blocker reported in this packet
- No stored analysis record reported
- No teacher feedback included

The interface must not replace missing data with

- failed
- incorrect
- incomplete student
- low performance
- approved
- safe

unless that meaning is explicitly supported by a packet field.

## Import reporting

Each import operation must report

- number of files selected
- number successfully imported
- number rejected
- number that replaced an existing project_id

Rejected files must not disappear silently.

T2 should expose a concise reason for each rejected file without displaying
arbitrary untrusted file content as HTML.

## Untrusted packet content

All imported packet strings are untrusted local file content.

Teacher Workspace rendering must use text-safe DOM operations or equivalent
escaping.

Imported strings must never be inserted as executable HTML.

Packet content must never

- create script elements
- create event-handler attributes
- alter authentication state
- change Worker configuration
- navigate the browser automatically
- activate teacher privileges

## T2 implementation architecture

The first implementation step after this contract should create a dedicated
teacher data module.

Suggested responsibility

assets/teacher-workspace-data.js

The module should contain pure or side-effect-minimized functions for

- validating a v1.7 student packet
- creating a normalized display model
- upserting by project_id
- deriving Overview counts
- deriving Review Queue flags and reasons
- deriving a Student Project Inspector model

The data module must not

- access teacher credentials
- call the Worker
- use network requests
- persist packet contents
- modify student project data
- write teacher feedback
- manipulate the DOM

Teacher Workspace UI code should consume the normalized model produced by this
module.

## T2 test boundary

Before T2 can be committed, automated tests must prove at minimum

- valid v1.7 packets are accepted
- wrong packet types are rejected
- wrong packet versions are rejected
- missing project_id is rejected
- malformed milestones are rejected
- rejected packets do not affect Overview
- duplicate project_id replaces the prior whole packet
- Overview counts follow this contract
- Review Queue flags follow this contract
- a project can carry multiple queue flags
- no-immediate-action is only used when no queue flag applies
- missing optional data remains neutral
- imported strings are rendered safely
- raw data and full-paper fields are neither expected nor reconstructed
- no persistence API is used by the T2 data module
- existing v1.7 packet and feedback behavior remains compatible
- existing student regressions continue to pass

## T2 non-goals

T2 does not yet

- change packet version 1.7
- add expanded inspection packets
- add assignment setup
- add persistent class rosters
- add server-side class storage
- add student accounts
- expose Research Chat transcripts
- add automatic grading
- write teacher decisions directly into student projects
- modify the Cloudflare Worker
- change production release manifests
- modify the frozen v2.16.0 manifest

## Development rule

The existing authenticated T1 shell remains the security boundary.

T2 data functionality may become visible only after the T1 server-verified
teacher session gate succeeds.

Every T2 implementation step must preserve the known-good production recovery
point and pass existing student regressions before it is considered for merge.
