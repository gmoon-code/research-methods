# Research Methods Studio v2.17 Teacher Workspace

## T3 Teacher Review and Feedback Export Contract

T2 is frozen at commit `9036a64fcbf964a33af92444d9ccab10b399ec1a`.

## Purpose

T3 adds explicit teacher review and local feedback-packet export to the authenticated Teacher Workspace.

T3 reuses the existing student-compatible feedback format

- packet type `rms_teacher_feedback`
- version `1.7`

T3 does not create a new feedback format or change the student review packet format.

## Existing feedback envelope

A T3 export must contain only

- `packet_type`
- `version`
- `created_at`
- `project_id`
- `student_alias`
- `checkpoints`
- `feedback`
- `competency_ratings`

Fixed values are

- `packet_type` = `rms_teacher_feedback`
- `version` = `1.7`
- `competency_ratings` = `[]` in the first T3 implementation

The existing student `applyTeacherFeedback()` path must accept the exported packet unchanged.

## Teacher decisions

Teacher checkpoint decisions are explicit actions.

Supported teacher-authored statuses are

- `approved`
- `revision_requested`

No software diagnostic may automatically select either status.

Approval must not be inferred from missing blockers, missing warnings, protocol lock, completed analysis, or software scores.

A `do_not_facilitate` diagnostic remains separate from teacher or institutional judgment.

## Checkpoint feedback

A checkpoint decision may contain

- existing milestone or checkpoint `id`
- explicit teacher status
- export-time `reviewedAt`
- teacher display name
- teacher comment
- teacher-authored conditions

Unknown checkpoint IDs must be rejected.

Conditions must never be generated automatically from packet warnings or blockers.

## General feedback

A teacher may also author separate feedback containing

- milestone when applicable
- stage when applicable
- teacher comment
- export-time creation timestamp

A meaningful teacher comment is required for a new general feedback item.

Software diagnostics must not silently become teacher feedback.

## Read-only student evidence

Imported student review packets remain read-only.

Teacher draft state must be separate from imported packet state.

T3 must not mutate imported

- milestones
- checkpoint evidence
- source summaries
- methods diagnostics
- analysis metadata
- writing metadata
- existing teacher feedback

Existing teacher feedback remains read-only history and is not copied automatically into a new export.

## Draft storage

Teacher review drafts exist only in page memory.

T3 must not persist draft or packet content in

- localStorage
- sessionStorage
- IndexedDB
- cookies
- Cache Storage
- a server
- the Cloudflare Worker
- a database

Existing teacher authentication may continue using its established sessionStorage token and expiry.

## Project switching

A draft belongs to exactly one `project_id`.

An unsaved non-empty draft must never silently transfer to another project.

Switching projects must require explicit discard or explicit confirmation.

## Empty drafts

Inspecting a project does not count as completing a review.

An empty draft must not be exported through the primary feedback action.

## Export

Before download, the teacher must be able to preview the exact validated feedback packet.

The export is a local JSON download initiated by an explicit teacher action.

Suggested filename

`rms-teacher-feedback-<project_id>.json`

Unsafe filename characters must be sanitized.

Export must not send feedback or student packet data over the network.

## Privacy

The feedback export must use an explicit allowlist.

It must not contain

- the full imported student packet
- raw dataset rows
- full paper text
- source text
- source notes
- Research Chat transcripts
- software diagnostic payloads
- teacher access code
- teacher session token
- browser-storage contents

## Competency ratings

The legacy feedback packet contains `competency_ratings`.

The first T3 implementation must export this field as an empty array.

T3 does not author competency ratings.

That capability belongs to a later Analytics milestone.

## Authentication and network boundary

T3 remains behind the existing signed teacher-session verification.

Review controls must not initialize before successful teacher verification.

T3 adds no Worker route, Worker secret, database, or feedback network request.

The established teacher-session verification remains the only Teacher Workspace network behavior.

## Text safety

Imported student strings and teacher-authored strings must be rendered through text-safe DOM operations.

T3 must not introduce dynamic `innerHTML` or `insertAdjacentHTML` for packet or feedback content.

## Accessibility

Review controls must be keyboard operable.

Inputs must have programmatic labels.

Validation and export status must be communicated accessibly.

Color must not be the only status indicator.

## T3 data layer

Feedback drafting and packet construction should remain pure data logic.

The data layer must not perform

- DOM operations
- authentication
- browser storage
- downloads
- network requests

Required capabilities include

- create an empty draft for one valid project
- validate or normalize a draft
- set or replace a checkpoint decision
- add or replace general teacher feedback
- determine whether exportable teacher work exists
- construct a validated `rms_teacher_feedback` version `1.7` packet

## Required tests

Data tests must verify

- exact feedback packet type and version
- exact project identity
- valid checkpoint IDs
- accepted `approved` and `revision_requested` statuses
- rejection of unsupported statuses
- explicit comments and conditions
- no automatic decision from diagnostics
- empty-review export rejection
- empty competency ratings
- imported-packet non-mutation
- existing-feedback non-copying
- omission of private student content

UI tests must verify

- authentication remains required
- imported evidence stays read-only
- drafts stay in memory
- no new persistence
- no feedback network request
- no dynamic innerHTML
- explicit export action
- safe project switching
- no competency-rating authoring
- the seven existing primary Teacher Workspace areas remain unchanged

Real-browser QA must verify approval, revision requests, comments, conditions, general feedback, packet preview, version 1.7 download, existing student-import compatibility, inert untrusted text, draft discard, project switching, no persistent storage, and no new network boundary.

## Completion criteria

T3 is complete only when all focused and regression tests pass, real-browser QA passes, student import compatibility is demonstrated, a clean local recovery commit exists, and no push or merge occurs without explicit authorization.
